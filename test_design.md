# Skill: test_design

## Purpose
Проектирование тестовой модели на основе проанализированных требований и сформированных задач.

Скил формирует структурированный набор проверок: позитивные и негативные сценарии, граничные условия,
проверки бизнес-правил и обработки ошибок, — с трассировкой до требований и задач.

Система управления тестами (например, Qase) приводится как пример; скил описывает работу с любой
аналогичной системой и не требует доступа к конкретной.

## Когда применять
После скилов `requirement_review` и `task_design`. Не применяется без результата анализа требований.

## Input
- структурированный анализ требований — результат скила `requirement_review`, с идентификаторами R-*
- перечень задач — результат скила `task_design`, с идентификаторами T-*
- указание на проект в системе управления тестами
- соглашения команды: структура модели (проект, сюиты, разделы), обязательные атрибуты проверки,
  правила приоритизации
- перечень существующих проверок проекта — для контроля дублей
- сведения о конфигурациях и окружениях, если проверки от них зависят

## Procedure
1. По каждому требованию и бизнес-правилу выделить проверяемые утверждения: что именно должно быть
   проверено и по какому наблюдаемому признаку.
2. Построить структуру тестовой модели: сюиты по функциональным областям, проверки внутри сюит.
3. Для каждой проверки определить: предусловия, шаги, ожидаемый результат, приоритет, тип, связанные
   идентификаторы R-* и T-*, конфигурацию, если она влияет на результат.
4. Обеспечить покрытие: позитивные сценарии, негативные сценарии, граничные значения, проверки
   бизнес-правил, проверки обработки ошибок и отказов.
5. Проверить уникальность проверок: объединить пересечения, устранить дубли, убедиться, что каждая
   проверка имеет собственную цель.
6. Присвоить проверкам идентификаторы C-* и построить матрицы трассируемости «требование → проверка»
   и «задача → проверка». Отметить непокрытые требования, отдельно — критичные.
7. Подготовить проверки к занесению в систему управления тестами и получить подтверждение по каждой:
   идентификатор созданной проверки либо сообщение об ошибке.
8. Сформировать список пробелов и открытых вопросов.

## Rules
- ожидаемый результат формулируется только из требований; предположение помечать явно как предположение
- не выдумывать поведение, не описанное в требованиях
- не дублировать проверки; каждая проверка должна иметь уникальную цель
- шаги проверки должны быть однозначны и воспроизводимы сторонним исполнителем
- не изменять и не удалять существующие проверки; не менять настройки проекта
- критичные требования обязаны иметь покрытие; отсутствие покрытия — это пробел, а не «проверим позже»
- при повторном запуске сверяться с уже созданными проверками и не создавать их повторно
- проверки, вытекающие из неоднозначных требований, не создавать до разрешения неоднозначности:
  выносить в открытые вопросы

## Output
Результат выполнения скила должен содержать:
- структуру тестовой модели
- перечень проверок: предусловия, шаги, ожидаемый результат, атрибуты
- матрицы трассируемости «требование → проверка» и «задача → проверка»
- отчёт покрытия: позитивные сценарии, негативные сценарии, граничные значения, бизнес-правила, ошибки
- список непокрытых и критичных без покрытия требований
- подтверждения создания: идентификатор каждой созданной проверки
- перечень пробелов и открытых вопросов

## Completion Criteria
Скил считается успешно выполненным, если:
- каждая проверка связана с требованием и имеет идентификатор C-*
- критические требования покрыты проверками
- покрыты позитивные и негативные сценарии, граничные значения и бизнес-правила
- дублей нет; каждая проверка уникальна
- по каждой проверке получено подтверждение создания
- пробелы и открытые вопросы перечислены и адресованы
- результат пригоден для передачи в тестирование без повторного проектирования
