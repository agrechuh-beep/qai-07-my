# QA-агент: требования → задачи → тестовая модель

Мультиагентная система на [opencode](https://opencode.ai) для регулярной работы QA-группы: разбор
требований, подготовка задач для команды разработки, проектирование тестовой модели и публикация
результатов в системах трекинга и управления тестами.

Работает как оркестратор и четыре субагента: каждый этап выполняет отдельный агент, оркестратор
проверяет результат по критериям качества и только после этого запускает следующий этап.

Все внешние системы упоминаются как примеры и заменяются аналогичными: система документации,
система трекинга задач, система управления тестами.

## Что нужно для запуска

1. **opencode** (проверено на v2.2.5). Проверка: `opencode --version`.
2. **Свой ключ провайдера моделей**, доступный как переменная окружения `CLOUDRU_API_KEY`
   (в примере — cloud.ru Foundation Models; ключ выдаётся в консоли провайдера). У каждого свой ключ:
   в репозитории его нет и быть не должно.

   ```bash
   # на текущую сессию
   export CLOUDRU_API_KEY="ваш-ключ"

   # или аккуратнее: значение в отдельном файле с правами 600
   mkdir -p ~/.config/opencode
   printf '%s' 'ваш-ключ' > ~/.config/opencode/cloudru.key
   chmod 600 ~/.config/opencode/cloudru.key
   echo 'export CLOUDRU_API_KEY="$(cat "$HOME/.config/opencode/cloudru.key")"' >> ~/.bashrc
   ```

3. **Доступ к внешним системам** — нужен только на этапах чтения требований и публикации:
   адрес инсталляции и токен для каждой системы (подробности в разделе «Подключение внешних систем»).
   Они задаются в локальном файле, который **не коммитится**.

> Ключи не коммитить. Конфиги репозитория ссылаются на переменные окружения и пути к файлам,
> а не на значения.

## Проверка готовности

Выполнить из корня репозитория:

```bash
opencode --version                        # версия opencode
opencode models | grep '^cloudru/'        # должно вернуться 4 модели
opencode run "Ответь одной строкой: READY"
```

Последняя команда запускает агента по умолчанию — `qa-orchestrator`.

| Что видно | Что это значит |
|---|---|
| `READY` | всё настроено, ключ подхватился |
| `Error: Missing authorization in request` | не задана `CLOUDRU_API_KEY` (или терминал не читает профиль) |
| `Model unavailable` | модель не объявлена в `opencode.json` или опечатка в её ключе |
| пустой список моделей | не загрузился провайдер: проверьте `opencode.json` и `opencode debug config` |

## Как запускать

Из корня репозитория:

```bash
opencode                      # интерактивный режим; агент по умолчанию — qa-orchestrator
opencode run --agent qa-orchestrator "Прогон 2026-11-10-01. Требования: <текст или ссылка>"
```

Что передать оркестратору:

- идентификатор прогона (например, `2026-11-10-01`) и каталог артефактов (по умолчанию `qa-artifacts/`);
- текст требований или ссылку на страницу документации, а также версию требований;
- соглашения команды: шаблон задачи, обязательные поля, приоритеты, структуру тестовой модели;
- на этапе публикации — проекты в системе трекинга задач и в системе управления тестами.

Субагенты запускаются **только оркестратором** — вручную их вызывать не нужно. Прямой запуск
(`opencode run --agent task-designer ...`) возможен только для отладки. Список агентов:
`opencode debug agents`.

## Роли агентов

| Агент | Режим | Что делает | Скил | Результат |
|---|---|---|---|---|
| `qa-orchestrator` | основной | планирует этапы, проверяет quality gate, запускает субагентов, формирует итоговый отчёт | — | манифест и отчёт прогона |
| `requirements-analyst` | субагент | разбирает требования, выявляет неоднозначности, противоречия и пробелы | `requirement-review` | `01-requirements-review.md` |
| `task-designer` | субагент | формирует артефакт задач для разработки (ничего не создаёт в трекере) | `task-design` | `02-task-spec.md` |
| `test-designer` | субагент | проектирует тестовую модель с трассировкой до требований | `test-design` | `03-test-spec.md` |
| `entity-publisher` | субагент | создаёт задачи и проверки в целевых системах по прошедшему gate артефакту | `entity-publication` | `04-publication-log.json` |

**Поток данных:** требования читаются из системы документации — их читает `requirements-analyst`
через MCP-инструменты, только на чтение. Задачи создаются в системе трекинга задач, проверки —
в системе управления тестами. Записывает во внешние системы только `entity-publisher` и только
по пройденному quality gate; остальные агенты во внешние системы не пишут.

Правила процесса целиком — в `AGENTS.md`: порядок этапов, quality gate G1–G5, зависимости этапов,
обработка ошибок, состав итогового отчёта.

## Артефакты прогона

Все результаты складываются в `qa-artifacts/<run-id>/`:

| Файл | Кто формирует | Содержание |
|---|---|---|
| `00-run.json` | оркестратор | манифест: версия требований, статусы этапов и gate, ошибки |
| `01-requirements-review.md` | `requirements-analyst` | требования с идентификаторами `R-*`, бизнес-правила, ограничения, риски, открытые вопросы |
| `02-task-spec.md` | `task-designer` | задачи `T-*` с критериями приёмки и матрицей трассируемости |
| `03-test-spec.md` | `test-designer` | проверки `C-*`, покрытие, матрицы «требование → проверка» и «задача → проверка» |
| `04-publication-log.json` | `entity-publisher` | по каждой сущности: создана или нет, идентификатор, ссылка |
| `05-summary-report.md` | оркестратор | итоговый отчёт по всему прогону |

Этапы обмениваются данными **только через файлы**: каждый `.md`-артефакт начинается с YAML-заголовка
(`run_id`, `stage`, `status`, `inputs`, `counts`, `ids`, `open_questions`), а идентификаторы `R-*`/`T-*`/`C-*`
сквозные и не меняются между этапами.

Результаты прогонов в репозиторий **не коммитятся**: в реальном прогоне артефакты содержат текст
требований, формулировки задач и ссылки на внутренние системы, а репозиторий несёт процесс, а не
данные. В git остаётся только синтетический пример `qa-artifacts/example-01/` — по нему видно формат.
Остальные каталоги прогонов закрыты правилом в `.gitignore`; при необходимости пример обновляется
вручную вместе с изменением контракта артефактов.

## Структура репозитория

```
AGENTS.md                       правила процесса: роли, артефакты, quality gate, ошибки, отчёт
opencode.json                   агент по умолчанию, провайдер моделей, 4 модели (секретов нет)
.opencode/agents/*.md           описания агентов: роль, вход, выход, права
.opencode/skills/<имя>/SKILL.md скилы этапов: процедура, правила, критерии завершения
.opencode/tools/atlassian-mcp.sh  запуск локального MCP-сервера для трекера и документации
.opencode/tools/allure-mcp.sh     запуск локального MCP-сервера для системы управления тестами
qa-artifacts/<run-id>/          результаты прогонов (в git не коммитятся, см. .gitignore)
qa-artifacts/example-01/        синтетический пример контракта артефактов — единственный в git
```

## Модели

Провайдер в примере — cloud.ru Foundation Models (OpenAI-совместимый API). В конфиге объявлены
четыре модели (цены провайдера, ₽ за 1 млн токенов):

| Ключ в конфиге | Модель | Вход | Выход | Контекст | Назначение |
|---|---|---|---|---|---|
| `qwen-qwen3.7-flash` | qwen/qwen3.7-flash | 5,34 | 23,14 | 1 000 000 | самый дешёвый: механические шаги |
| `deepseek-ai-deepseek-v4-flash` | deepseek-ai/DeepSeek-V4-Flash | 43,30 | 86,58 | 1 048 576 | по умолчанию: reasoning, 1M |
| `qwen-qwen3-coder-next` | Qwen/Qwen3-Coder-Next | 122 | 244 | 262 144 | кодовый профиль |
| `deepseek-ai-deepseek-v4-pro` | deepseek-ai/DeepSeek-V4-Pro | 183 | 732 | 1 048 576 | сложный анализ требований |

- **Сменить модель агента** — строка `model:` в его файле `.opencode/agents/<имя>.md`.
- **Сменить модель по умолчанию** — ключ `model` в `opencode.json`.
- **Добавить модель** — дописать запись в `providers.<провайдер>.models` в `opencode.json`; актуальные
  идентификаторы возвращает каталог моделей провайдера.

## Подключение внешних систем (MCP)

Внешние системы подключены двумя локальными MCP-серверами, которые opencode запускает по stdio:

| Сервер | Системы | Пакет | Инструментов |
|---|---|---|---|
| `atlassian` | документация и трекер задач (в примере Jira и Confluence) | [mcp-atlassian](https://github.com/sooperset/mcp-atlassian) | 43: 22 на чтение, 21 на запись |
| `testops` | управление тестами (в примере Allure TestOps) | [allure-testops-mcp](https://github.com/mshegolev/allure-testops-mcp) | 20: 13 на чтение, 7 на запись |

Оба сервера берут адреса и токены из окружения, которое им передаёт обёртка из `.opencode/tools/`.
В самих обёртках и в конфигах нет ни адресов, ни токенов: адрес обязателен и задаётся снаружи,
токен читается из файла.

### Что нужно на машине

| Что | Зачем |
|---|---|
| сетевой доступ к системам | инсталляции обычно доступны только из корпоративной сети (VPN) |
| токен документации и **отдельный** токен трекера | персональный токен (PAT) одного приложения не работает в другом |
| токен системы управления тестами | API-токен из профиля пользователя |
| локальный файл окружения с адресами и путями | значения хранятся вне репозитория (см. ниже) |
| два Python-пакета MCP-серверов | ставятся в отдельные окружения |

```bash
# MCP-серверы в отдельных окружениях
uv venv --python 3.12 ~/.local/share/mcp/atlassian/venv
uv pip install --python ~/.local/share/mcp/atlassian/venv/bin/python3 mcp-atlassian
uv venv --python 3.12 ~/.local/share/mcp/testops/venv
uv pip install --python ~/.local/share/mcp/testops/venv/bin/python3 allure-testops-mcp
```

Если пути отличаются от значений по умолчанию, они переопределяются переменными окружения
(`MCP_ATLASSIAN_BIN`, `MCP_ALLURE_BIN`).

### Локальные значения: адреса и пути к токенам

Всё, что зависит от конкретной машины и инсталляции, лежит в одном файле вне репозитория:

```bash
mkdir -p ~/.config/opencode/secrets && chmod 700 ~/.config/opencode/secrets

# токены: значение пишется в файл, а не в чат и не в конфиг
printf '%s' '<PAT документации>'   > ~/.config/opencode/secrets/confluence.token && chmod 600 ~/.config/opencode/secrets/confluence.token
printf '%s' '<PAT трекера>'        > ~/.config/opencode/secrets/jira.token       && chmod 600 ~/.config/opencode/secrets/jira.token
printf '%s' '<API-токен тестов>'   > ~/.config/opencode/secrets/testops.token    && chmod 600 ~/.config/opencode/secrets/testops.token

# адреса инсталляций — тоже вне репозитория
cat > ~/.config/opencode/mcp.env <<'EOF'
JIRA_URL=https://jira.example.com
CONFLUENCE_URL=https://confluence.example.com
ALLURE_URL=https://testops.example.com
EOF
chmod 600 ~/.config/opencode/mcp.env
```

Обёртки читают этот файл автоматически (`MCP_ATLASSIAN_ENV_FILE` / `MCP_ALLURE_ENV_FILE`
переопределяют путь). Если адрес не задан, сервер не запустится и скажет, что именно пропущено.

Переменные, которыми можно переопределить поведение: `JIRA_URL`, `CONFLUENCE_URL`, `ALLURE_URL`,
`JIRA_SSL_VERIFY` / `CONFLUENCE_SSL_VERIFY` (для самоподписанных сертификатов — `false`),
`ALLURE_SSL_VERIFY`, `ALLURE_ENABLE_WRITE`, `TOOLSETS`, `MCP_JIRA_TOKEN_FILE`,
`MCP_CONFLUENCE_TOKEN_FILE`, `MCP_ALLURE_TOKEN_FILE`, `*_SECRETS_DIR`. Подробности — в комментариях
к скриптам `.opencode/tools/`.

### Регистрация в opencode

```bash
opencode mcp add atlassian --global -- bash "$PWD/.opencode/tools/atlassian-mcp.sh"
opencode mcp add testops   --global -- bash "$PWD/.opencode/tools/allure-mcp.sh"
opencode mcp list          # ожидаем: ✓ atlassian connected и ✓ testops connected
```

> **Почему регистрация глобальная.** В проверенной сборке (opencode v2.2.5) список MCP-серверов агенты
> получают из глобального конфига: служба opencode читает конфигурацию того каталога, в котором она
> запущена, поэтому проектная секция `mcp` видна не всегда — после `opencode service restart` агент
> перестаёт видеть инструменты из неё. Глобальная запись работает независимо от этого, поэтому она
> и является рабочей; секция `mcp` в проектном файле оставлена как описание замысла.

### Состав инструментов

- Сервер `atlassian`: 43 инструмента из отобранных наборов — задачи, поиск, комментарии, переходы
  по статусам, страницы документации. Доски, ворклоги, вложения и аналитика исключены как ненужные
  этапам; наборы заданы явно, чтобы состав не менялся при обновлении пакета.
- Сервер `testops`: 20 инструментов, из них 7 на запись включаются флагом `ALLURE_ENABLE_WRITE=true`.
  Инструменты записи включены намеренно: они нужны этапу публикации, а кто именно может писать,
  решают права агентов.

Имена имеют вид `<сервер>_<инструмент>`: `atlassian_jira_search`, `atlassian_confluence_get_page`,
`testops_allure_list_projects`, `testops_allure_create_test_case`.

### Кому что разрешено

Правила лежат в блоке `permissions` каждого агента (`.opencode/agents/*.md`):

| Агент | Документация и трекер | Управление тестами |
|---|---|---|
| `qa-orchestrator` | только чтение | только чтение |
| `requirements-analyst` | только чтение | нет доступа |
| `task-designer`, `test-designer` | нет доступа | нет доступа |
| `entity-publisher` | чтение и запись | чтение и запись |

У каждого агента сначала идёт общий запрет (`atlassian_*` / `testops_*`), который перекрывается
разрешениями ниже по списку. Запрет работает на уровне каталога инструментов, а не уговоров:
у дизайнеров MCP-инструментов нет вовсе, поэтому случайная запись во внешнюю систему невозможна.

### Проверка

```bash
opencode mcp list            # ✓ atlassian connected и ✓ testops connected
opencode run --agent requirements-analyst "Вызови atlassian_confluence_search с запросом 'тест'"
opencode run --agent qa-orchestrator "Вызови testops_allure_list_projects и покажи 5 проектов"
```

Если приходит ошибка разрешения имени хоста — нет сетевого доступа к системам (нужен VPN).
Коды `401` и `403` означают проблему с токеном, а не с сервером; `404` в теле ответа API —
что авторизация прошла, а маршрут указан неверно.

Проверено на рабочем контуре: поиск и чтение страниц документации, поиск и чтение задач трекера,
чтение справочников и проектов системы управления тестами через MCP работают. Путь записи проверяется
на тестовом проекте — во внешних системах ничего не создаётся без явного решения оркестратора.

## Безопасность и секреты

- **В репозитории нет значений ключей.** Конфиги ссылаются на переменные окружения
  (`{env:CLOUDRU_API_KEY}`) и на файлы с токенами; адреса инсталляций задаются локальным файлом
  окружения, которого в репозитории тоже нет.
- **Соглашение о хранении токенов:** один файл на приложение, каталог с правами `700`, файл `600`,
  владелец — рабочая учётная запись. Путь передаётся переменной окружения, а не прописан в коде.
- **Права агентов — единственный барьер записи.** У системы управления тестами нет области «только
  чтение»: токен наследует права пользователя. Поэтому ограничение записи обеспечивается правилами
  агентов, а не свойствами токена. Для строгого контура используйте отдельную учётную запись с
  урезанной ролью и её токен.
- **Всё, что исполняется под рабочей учётной записью, видит токены** — MCP-серверы получают их через
  окружение процесса, поэтому секретность пути к файлу доступа не ограничивает. Следствие: не
  запускать под этой учётной записью недоверенный код и пинить версии сторонних пакетов.
- **Перед публикацией репозитория наружу** проверьте, что адреса инсталляций, локальные пути и имена
  внутренних систем остались в локальном файле окружения, а не в коммитах.

## Если что-то не работает

- **`Missing authorization in request`** — не задана `CLOUDRU_API_KEY`; проверьте
  `echo ${CLOUDRU_API_KEY:+есть}` и что терминал читает профиль.
- **`Model unavailable`** — ключ модели не совпадает с записью в `opencode.json`.
- **`provider.no-route`** — конфиг не подхватился: запускайте opencode из корня репозитория,
  смотрите `opencode debug config`.
- **Публикация не выполнялась** — это нормально, если в `00-run.json` нет пройденного gate: издатель
  не публикует без решения оркестратора.
- **Агент не найден** — `opencode debug agents` покажет, какие агенты видны из текущего каталога.
- **`No MCP servers configured`** — серверы не зарегистрированы в глобальном конфиге: выполните
  `opencode mcp add <имя> --global -- …`.
- **`✓ … connected`, но у агента нет MCP-инструментов** — для `task-designer` и `test-designer`
  это норма: доступ закрыт правилами. Состав прав виден в `opencode debug agents`.
- **Обёртка не запускается и просит адрес** — не заполнен локальный файл окружения
  (`~/.config/opencode/mcp.env`); см. раздел «Локальные значения».
- **`401` от системы управления тестами** — проверьте схему авторизации: принимается только
  префикс `Api-Token`.
