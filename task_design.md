# Skill: task_design

## Purpose
Формирование задач для команды разработки на основе проанализированных требований.

Скил превращает результат анализа требований в набор задач с понятной целью, описанием, критериями
приёмки и приоритетом, и обеспечивает связь каждой задачи с требованием, из которого она выведена.

Система трекинга задач (например, Jira) приводится как пример баг-трекинга и трекинга задач; скил
описывает работу с любой аналогичной системой и не требует доступа к конкретной.

## Когда применять
После скила `requirement_review` и до скила `test_design`. Не применяется, если анализ требований
не выполнен, а также если анализ выявил противоречия или критический недостаток информации —
в этом случае сначала эскалация (см. агентскую инструкцию).

## Input
- структурированный анализ требований — результат скила `requirement_review`, с идентификаторами R-*
- указание на проект в системе трекинга задач
- соглашения команды: шаблон задачи, обязательные поля, значения приоритетов, правила связывания задач
- перечень существующих задач проекта — для контроля дублей

## Procedure
1. Отобрать требования, реализуемые разработкой: функциональные требования, изменения поведения,
   ограничения, исполняемые в коде. Требования, не требующие работ по разработке, вынести в отдельный
   список с обоснованием (например, уже реализовано, относится только к документации, не входит в объём).
2. Определить границы задачи: одна задача — одна проверяемая единица функциональности.
3. Сформировать поля каждой задачи: заголовок, цель, описание функциональности, критерии приёмки,
   приоритет, зависимости, источник (идентификаторы R-*), тип, затронутые области продукта.
4. Проверить критерии приёмки: проверяемость, выводимость из требований, отсутствие описания реализации.
5. Проверить дубли: сопоставить кандидатов с существующими задачами проекта и между собой.
6. Присвоить задачам идентификаторы T-* и построить матрицу трассируемости «требование → задача».
   Отметить требования, не покрытые задачами.
7. Подготовить задачи к созданию в системе трекинга и получить подтверждение создания по каждой:
   идентификатор созданной задачи либо сообщение об ошибке.
8. Сформировать открытые вопросы по требованиям, из которых задачу нельзя сформулировать однозначно.

## Rules
- каждая задача имеет основание в требовании; задачи «на всякий случай» не создавать
- не выдумывать функциональность, отсутствующую в требованиях
- не описывать реализацию и не выбирать техническое решение, если это не задано требованиями
- не дублировать задачи
- не изменять, не закрывать и не удалять существующие задачи; не менять настройки проекта
- критерии приёмки формулировать как наблюдаемый результат, а не как действие разработчика
- приоритет присваивать по соглашениям команды, а не по собственному усмотрению
- при повторном запуске сверяться с уже созданными задачами и не создавать их повторно
- открытые вопросы не превращать в задачу с неясной формулировкой: они идут в отчёт и в эскалацию

## Output
Результат выполнения скила должен содержать:
- перечень задач: поля каждой задачи в виде, готовом к занесению в систему трекинга
- матрицу трассируемости «требование → задача»
- список требований, не требующих задач по разработке, с обоснованием
- список отклонённых кандидатов (дубли, выход за границы объёма) с причиной
- подтверждения создания: идентификатор каждой созданной задачи
- перечень открытых вопросов по задачам

Результат структурируется так, чтобы следующий этап мог связать проверки с задачами без повторного разбора.

## Completion Criteria
Скил считается успешно выполненным, если:
- у каждой задачи есть источник в требованиях и идентификатор T-*
- у каждой задачи есть проверяемые критерии приёмки
- каждой задаче присвоен приоритет по соглашениям команды
- дублей нет; каждая задача описывает отдельную проверяемую единицу функциональности
- каждое требование либо покрыто задачей, либо явно объяснено, почему задачи не требуется
- по каждой задаче получено подтверждение создания
- открытые вопросы перечислены и адресованы
