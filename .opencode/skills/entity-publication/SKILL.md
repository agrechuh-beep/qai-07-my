## Purpose
Создание сущностей во внешних системах по артефактам, прошедшим quality gate.

Скил выполняет только публикацию: принимает готовый артефакт, сверяет его с текущим состоянием системы,
создаёт сущности, подтверждает результат чтением и фиксирует идентификаторы обратно в артефакт.
Проектирование, пересмотр содержания задач и проверок в задачи скила не входят.

Системы приводятся как примеры и могут быть заменены аналогичными: система трекинга задач
(например, Jira) и система управления тестами (например, Qase).

Публикация выполняется инструментами самих систем: для Jira и Confluence это MCP-инструменты
`atlassian_jira_*` и `atlassian_confluence_*` — например, `atlassian_jira_create_issue`,
`atlassian_jira_update_issue`, `atlassian_confluence_create_page`; для системы управления тестами —
`testops_allure_create_test_case` и `testops_allure_update_test_case`. Вызов REST API через оболочку —
запасной путь, если MCP-сервер недоступен. Подтверждение создания выполняется чтением через тот же
канал: инструментами чтения MCP или запросом API — например, `testops_allure_get_test_case`
и `testops_allure_list_test_cases` для проверки, что сущность действительно создана и не дублируется.

## Когда применять
После того как оркестратор подтвердил gate соответствующего артефакта. Публикация задач требует
пройденного G2, публикация проверок — G3, обе — пройденного G4.

Не применяется: до проверки gate; для артефакта со статусом `blocked`; для пунктов, вынесенных
в открытые вопросы, — они не публикуются до разрешения неоднозначности.

## Input
- артефакт `02-task-spec.md` и/или `03-test-spec.md`
- манифест `00-run.json` с подтверждёнными статусами gate
- указание на проект в целевой системе
- соглашения команды: обязательные поля, шаблоны, правила связывания

## Procedure
1. Проверить в манифесте статус gate для артефакта. Если gate не пройден — публикацию не выполнять
   и сообщить об этом оркестратору.
2. Сверить артефакт с текущим состоянием системы: найти сущности, созданные в этом прогоне ранее,
   и возможные дубли по смыслу.
3. Публиковать по одной сущности: заполнять поля из артефакта, фиксировать ответ системы.
4. Подтвердить каждую созданную сущность чтением из системы.
5. Записать идентификатор и ссылку обратно в артефакт рядом с пунктом и в `04-publication-log.json`.
6. При частичной неудаче продолжить остальные сущности, неудачные зафиксировать с причиной.
7. Вернуть оркестратору сводку: сколько создано, сколько не удалось и почему.

## Rules
- публиковать только то, что прошло gate; пункты из открытых вопросов не публиковать
- создание — единственная разрешённая операция изменения
- не изменять, не закрывать, не удалять существующие сущности и не менять настройки проекта
- идемпотентность: повторный запуск не создаёт дубли — сначала искать уже созданное в системе
  и в журнале публикации прогона
- каждая сущность подтверждается чтением из системы, а не предположением об успехе
- идентификаторы внешних систем не выдумывать: только те, что вернула система
- персональные и чувствительные данные в систему не переносить
- при недоступности системы останавливается только эта публикация; остальные ветки прогона
  продолжаются (см. матрицу зависимостей в агентской инструкции)

## Разрешения по системам
**Система трекинга задач (например, Jira) — создание задач.**
Разрешено: получать информацию о проекте; проверять существующие задачи; создавать новые задачи;
заполнять атрибуты задач; получать подтверждение создания каждой задачи.
Запрещено: изменять существующие задачи; удалять задачи; менять их статусы; закрывать задачи;
менять настройки проекта.

**Система управления тестами (например, Qase) — создание тестовой модели.**
Разрешено: получать информацию о проекте; проверять существующие проверки; создавать новые проверки;
заполнять атрибуты проверок; получать подтверждение создания каждой проверки.
Запрещено: изменять существующие проверки; удалять проверки; менять их статусы; менять настройки проекта.

## Артефакт
`<артефакты>/<run-id>/04-publication-log.json` — журнал публикации:

```json
{
  "run_id": "2026-11-07-01",
  "targets": [
    {"artifact": "02-task-spec.md", "system": "tracker", "item": "T-1",
     "status": "created", "id": "PRJ-1234", "url": "https://...", "verified": true},
    {"artifact": "03-test-spec.md", "system": "tms", "item": "C-4",
     "status": "failed", "error": "timeout"}
  ]
}
```

Идентификаторы дублируются в самом артефакте рядом с соответствующим пунктом, чтобы следующий этап
и повторный запуск видели, что уже создано.

## Output
- `04-publication-log.json` с результатом по каждой сущности
- обновлённые артефакты с идентификаторами внешних систем
- перечень неудачных публикаций с причиной и указанием, что нужно для повтора

## Completion Criteria
Скил считается успешно выполненным, если:
- gate соответствующего артефакта подтверждён в манифесте
- по каждой сущности известно состояние: создана (с идентификатором) или не создана (с причиной)
- созданные сущности подтверждены чтением из системы
- в артефактах проставлены идентификаторы внешних систем
- дублей не создано
- неудачные публикации перечислены и пригодны для повторного запуска без создания дублей
