> Версия 3. Изменения: скил формирует только артефакт и больше не создаёт сущности в системе трекинга —
> создание вынесено в скил `entity-publication` и выполняется после quality gate.

## Purpose
Формирование артефакта задач для команды разработки на основе проанализированных требований.

Скил превращает результат анализа требований в набор задач с понятной целью, описанием, критериями
приёмки и приоритетом, и обеспечивает связь каждой задачи с требованием, из которого она выведена.

Скил только проектирует артефакт: во внешние системы не пишет, доступ к системе трекинга задач
на этом этапе не требуется. Система трекинга задач (например, Jira) приводится ниже как пример того,
куда артефакт будет передан на следующем этапе.

## Когда применять
После скила `requirement-review` и до публикации. Не применяется, если анализ требований не выполнен,
а также если анализ выявил противоречия или критический недостаток информации — в этом случае сначала
эскалация (см. агентскую инструкцию).

## Input
- артефакт анализа требований `01-requirements-review.md` с идентификаторами R-*
- соглашения команды: шаблон задачи, обязательные поля, значения приоритетов, правила связывания задач
- если передан перечень существующих задач проекта — учитывается при формировании; окончательная
  проверка дублей выполняется на этапе публикации

Внешние системы на входе не требуются: все необходимые данные уже содержатся в артефакте анализа.

## Procedure
1. Отобрать требования, реализуемые разработкой: функциональные требования, изменения поведения,
   ограничения, исполняемые в коде. Требования, не требующие работ по разработке, вынести в отдельный
   список с обоснованием (например, уже реализовано, относится только к документации, не входит в объём).
2. Определить границы задачи: одна задача — одна проверяемая единица функциональности.
3. Сформировать поля каждой задачи: заголовок, цель, описание функциональности, критерии приёмки,
   приоритет, зависимости, источник (идентификаторы R-*), тип, затронутые области продукта.
4. Проверить критерии приёмки: проверяемость, выводимость из требований, отсутствие описания реализации.
5. Проверить уникальность внутри артефакта: задачи не должны пересекаться по объёму и дублировать
   друг друга. Сопоставление с существующими задачами проекта выполняется на этапе публикации.
6. Присвоить задачам идентификаторы T-* и построить матрицу трассируемости «требование → задача».
   Отметить требования, не покрытые задачами.
7. Подготовить артефакт к передаче: заполнить поля, необходимые для создания задачи, и отметить
   требования, из которых задачу нельзя сформулировать однозначно.
8. Сформировать открытые вопросы по требованиям с неоднозначной трактовкой.

## Rules
- каждая задача имеет основание в требовании; задачи «на всякий случай» не создавать
- не выдумывать функциональность, отсутствующую в требованиях
- не описывать реализацию и не выбирать техническое решение, если это не задано требованиями
- не создавать, не изменять и не удалять сущности в системе трекинга задач: это делает `entity-publication`
- критерии приёмки формулировать как наблюдаемый результат, а не как действие разработчика
- приоритет присваивать по соглашениям команды, а не по собственному усмотрению
- при повторном запуске опираться на предыдущий артефакт и записи публикации, не формировать заново
  то, что уже опубликовано
- открытые вопросы не превращать в задачу с неясной формулировкой: они идут в артефакт и в эскалацию

## Артефакт
`<артефакты>/<run-id>/02-task-spec.md` с обязательным YAML-заголовком:
`run_id`, `stage: task-design`, `status` (`done` / `partial`), `inputs` (путь к `01-requirements-review.md`),
`counts` (задач всего, по приоритетам, требований без задач), `ids` (диапазон T-*), `open_questions`.

Разделы артефакта: перечень задач с полями для создания, матрица трассируемости, требования без задач,
отклонённые кандидаты, открытые вопросы.

## Output
Артефакт `02-task-spec.md` должен содержать:
- перечень задач: поля каждой задачи в виде, готовом к публикации
- матрицу трассируемости «требование → задача»
- список требований, не требующих задач по разработке, с обоснованием
- список отклонённых кандидатов (внутренние дубли, выход за границы объёма) с причиной
- перечень открытых вопросов по задачам

Результат структурируется так, чтобы следующий этап мог связать проверки с задачами без повторного разбора.

## Completion Criteria
Скил считается успешно выполненным, если:
- артефакт `02-task-spec.md` создан и имеет корректный YAML-заголовок
- у каждой задачи есть источник в требованиях и идентификатор T-*
- у каждой задачи есть проверяемые критерии приёмки
- каждой задаче присвоен приоритет по соглашениям команды
- внутри артефакта нет дублей; каждая задача описывает отдельную проверяемую единицу функциональности
- каждое требование либо покрыто задачей, либо явно объяснено, почему задачи не требуется
- открытые вопросы перечислены и адресованы

Подтверждение создания сущностей в критерии завершения не входит: это задача следующего этапа
(`entity-publication`) после проверки quality gate оркестратором.
