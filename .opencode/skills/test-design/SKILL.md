> Версия 3. Изменения: скил формирует только артефакт и больше не создаёт проверки в системе управления
> тестами — создание вынесено в скил `entity-publication` и выполняется после quality gate.

## Purpose
Проектирование тестовой модели на основе проанализированных требований и сформированного артефакта задач.

Скил формирует структурированный набор проверок: позитивные и негативные сценарии, граничные условия,
проверки бизнес-правил и обработки ошибок, — с трассировкой до требований и задач.

Скил только проектирует артефакт: во внешние системы не пишет, доступ к системе управления тестами
на этом этапе не требуется. Система управления тестами (например, Qase) приводится как пример того,
куда артефакт будет передан на следующем этапе.

## Когда применять
После скилов `requirement-review` и `task-design`. Не применяется без артефакта анализа требований.
От недоступности внешних систем не зависит: работает с артефактами предыдущих этапов.

## Input
- артефакт анализа требований `01-requirements-review.md` с идентификаторами R-*
- артефакт задач `02-task-spec.md` с идентификаторами T-*
- соглашения команды: структура модели (проект, сюиты, разделы), обязательные атрибуты проверки,
  правила приоритизации
- если передан перечень существующих проверок проекта — учитывается при формировании; окончательная
  проверка дублей выполняется на этапе публикации
- сведения о конфигурациях и окружениях, если проверки от них зависят

## Procedure
1. По каждому требованию и бизнес-правилу выделить проверяемые утверждения: что именно должно быть
   проверено и по какому наблюдаемому признаку.
2. Построить структуру тестовой модели: сюиты по функциональным областям, проверки внутри сюит.
3. Для каждой проверки определить: предусловия, шаги, ожидаемый результат, приоритет, тип, связанные
   идентификаторы R-* и T-*, конфигурацию, если она влияет на результат.
4. Обеспечить покрытие: позитивные сценарии, негативные сценарии, граничные значения, проверки
   бизнес-правил, проверки обработки ошибок и отказов.
5. Проверить уникальность внутри артефакта: объединить пересечения, устранить дубли, убедиться,
   что каждая проверка имеет собственную цель. Сопоставление с существующими проверками проекта
   выполняется на этапе публикации.
6. Присвоить проверкам идентификаторы C-* и построить матрицы трассируемости «требование → проверка»
   и «задача → проверка». Отметить непокрытые требования, отдельно — критичные.
7. Подготовить артефакт к передаче: заполнить атрибуты, необходимые для создания проверки, и отметить
   проверки, которые нельзя публиковать до разрешения неоднозначности.
8. Сформировать список пробелов и открытых вопросов.

## Rules
- ожидаемый результат формулируется только из требований; предположение помечать явно как предположение
- не выдумывать поведение, не описанное в требованиях
- не дублировать проверки; каждая проверка должна иметь уникальную цель
- шаги проверки должны быть однозначны и воспроизводимы сторонним исполнителем
- не создавать, не изменять и не удалять сущности в системе управления тестами: это делает `entity-publication`
- критичные требования обязаны иметь покрытие; отсутствие покрытия — это пробел, а не «проверим позже»
- при повторном запуске опираться на предыдущий артефакт и записи публикации, не формировать заново
  то, что уже опубликовано
- проверки, вытекающие из неоднозначных требований, не подготавливать к публикации до разрешения
  неоднозначности: выносить в открытые вопросы

## Артефакт
`<артефакты>/<run-id>/03-test-spec.md` с обязательным YAML-заголовком:
`run_id`, `stage: test-design`, `status` (`done` / `partial`), `inputs` (пути к `01-requirements-review.md`
и `02-task-spec.md`), `counts` (проверок всего, по типам, критичных без покрытия), `ids` (диапазон C-*),
`open_questions`.

Разделы артефакта: структура модели, перечень проверок с атрибутами, матрицы трассируемости,
отчёт покрытия, непокрытые требования, пробелы и открытые вопросы.

## Output
Артефакт `03-test-spec.md` должен содержать:
- структуру тестовой модели
- перечень проверок: предусловия, шаги, ожидаемый результат, атрибуты
- матрицы трассируемости «требование → проверка» и «задача → проверка»
- отчёт покрытия: позитивные сценарии, негативные сценарии, граничные значения, бизнес-правила, ошибки
- список непокрытых и критичных без покрытия требований
- перечень пробелов и открытых вопросов

## Completion Criteria
Скил считается успешно выполненным, если:
- артефакт `03-test-spec.md` создан и имеет корректный YAML-заголовок
- каждая проверка связана с требованием и имеет идентификатор C-*
- критические требования покрыты проверками
- покрыты позитивные и негативные сценарии, граничные значения и бизнес-правила
- внутри артефакта нет дублей; каждая проверка уникальна
- пробелы и открытые вопросы перечислены и адресованы
- артефакт пригоден для передачи в тестирование без повторного проектирования

Подтверждение создания проверок в критерии завершения не входит: это задача следующего этапа
(`entity-publication`) после проверки quality gate оркестратором.
